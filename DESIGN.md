# bcns-data — Design

Implements `REQUIREMENTS.md` (R1–R39). Every table, policy, view, RPC, connector, job, and SB panel is
specified here so the build session makes no design calls. Section 10 maps each requirement to its
section. Section 11 ("Needs Nate") lists what this document could not decide.

Conventions: Postgres 17 on the shared Supabase Pro project. Base tables live in schema **`data`**;
the dashboard-facing contract lives in schema **`api`**; PostgREST exposes **`api` only**. All
timestamps are `timestamptz`; day buckets are `date` in the client's timezone; money is
`amount_minor bigint` + `currency char(3)`. `client_id` is the first column of every primary key,
unique key, and index on tenant data. Names below are final — the build uses them verbatim.

## 0. Design calls made here (not in REQUIREMENTS)

Recorded so the build does not re-decide them. Each is reversible on a concrete failure.

| # | Call | Why |
|---|------|-----|
| D1 | Base tables in schema `data`, not `public`; PostgREST exposed schemas = `api` only. | R13 becomes structural: nothing outside `api` is reachable over HTTP. |
| D2 | Policies compare `client_id = (select data.active_client_id())`. The function reads the JWT claim **and** checks `memberships` + `clients.status = 'active'` once per statement (Postgres InitPlan), not per row. | R2 and R4 hold on the next request, not the next token refresh; cost is one index lookup per query. |
| D3 | The tenant-role claim is named **`client_role`**, not `role`. | Supabase reserves the `role` claim (`authenticated`/`anon`) for PostgREST role switching; overwriting it breaks every request. REQUIREMENTS' `role` is satisfied by `client_role`. |
| D4 | `security_invoker` views require `authenticated` to hold SELECT on the `data` tables they read (RLS still filters). "No grant on base tables" (R13) is read as "no HTTP path to base tables" — enforced by D1 — plus **no grant at all** on `source_tokens`, `connector_schedule`, `connector_runs`, `notifications`. | `security_invoker` is the only view mode that applies the caller's RLS; a `security_definer` view runs as its owner and would bypass RLS. |
| D5 | Raw is append-only **and content-deduplicated**: a fetched row is inserted only when its `payload_hash` differs from the newest stored row for `(client_id, source, entity, external_id)` (tracked in `data.raw_latest`). PK `(client_id, source, entity, external_id, fetched_at)`, range-partitioned by month of `fetched_at`. Normalize takes the newest row per key by `(source_updated_at, fetched_at)`. | R6/R7: every *change* is kept and replay is deterministic; re-fetching an unchanged full list (Monday board hourly, Meta campaign list 4×/day) writes nothing. Without dedupe a 500-item board is 12,000 raw rows/day/client. |
| D6 | Connector health is **computed by the worker into `data.connector_health`** each tick; `api.connector_health_v1` is a plain view over it. | Dashboards cannot read `connector_schedule`/`connector_runs` (D4), and a per-read scan of runs would not scale. |
| D7 | Non-secret per-source config (shop domain, ad account id, board id, Drive folder id, column ids) lives in `connector_schedule.config jsonb`; `source_tokens` holds secrets only. | One place per concern; tokens table stays minimal and service-role-only. |
| D8 | Meta campaigns and ads are `records` rows (`kind = 'campaign' | 'ad'`) — the "doesn't fit → records" rule. Meta creative images are downloaded into Storage as `media(source='meta')`. | No entity table; Top Creative joins `daily_metrics → records → media`. Meta CDN URLs expire; a local copy makes the panel stable and thumbnails uniform. |
| D9 | Signed URLs are minted client-side by the Storage SDK **after** `api.download_url(media_id)` records the bytes and checks the budget; the Storage SELECT policy is the enforcement (R22). The shared data-client package exposes one `downloadUrl()` that does both. | SQL cannot call the Storage signing endpoint; the policy is the only thing that can deny the object itself. |
| D10 | Thumbnails are generated by the worker (next tick after upload, ≤ 5 min) with `sharp`, 512 px longest edge, JPEG, into `<client_id>/thumb/`. Videos get no thumbnail in v1. | Storage uploads cannot run code; "at upload" (R21) is read as "before the file is browsable". |
| D11 | Worker claims work with `UPDATE … FOR UPDATE SKIP LOCKED` and an 8-minute lease (2 × `RUN_BUDGET_MS`); each run has a 4-minute wall-clock budget and persists its cursor after every page. Claimed rows run **in parallel**; the rate-limit semaphore is keyed per `(source, client_id)`, never per source. | R27/R28: a 260-page backfill spans ticks with no state outside the DB; two overlapping ticks cannot double-process; a crashed job's lease expires within two ticks. R26: one client's Shopify throttle never queues another client's Shopify run. |
| D12 | Three worker queue indexes are cross-tenant, without `client_id` leading: `connector_schedule (next_run_at) where enabled`, `media (created_at) where <thumbnail pending>`, `media (purge_after) where deleted_at is not null`. | They serve service-role-only queue scans and are ordered by the queue's sort key. Every other index leads with `client_id`. |
| D13 | Tokens are stored plaintext in `data.source_tokens` (RLS enabled, zero policies → service role only). | Requirement says "readable only by the service role"; anyone with the backup also has the service key. Supabase Vault is the upgrade if a backup ever leaves Supabase. |
| D14 | bcns alerts go out from the worker via Resend to `BCNS_ALERT_EMAIL`, deduped through `data.notifications.dedupe_key`. | The worker is the only always-running platform code; the pipeline's notify router is a separate repo. |
| D15 | Pooled-egress alert (R23) is computed from `sum(egress_ledger.bytes)` across clients against `EGRESS_ALLOWANCE_BYTES` (env, default 250 GB), not from the Supabase Management API. | No external dependency; the ledger over-counts (requested, not transferred bytes), which is the conservative direction for an 80 % alert. |
| D16 | `owner` may **remove** a member via `api.remove_member`; **adding** a user stays a bcns task (needs the Auth admin API, which needs the service key). | Matches "bcns creates users" while giving `owner` a real power. Invite flow is a later RPC + edge function if a client asks. |
| D17 | Dashboards self-report their version through `api.report_dashboard_version` on boot. | `dashboard_versions` stays correct without a bcns task. |
| D18 | Inventory history is a once-per-local-day snapshot written by the Shopify connector into `daily_metrics(metric='inventory_units')`. | The Overview inventory tile needs a trend line; Shopify exposes only current levels. |
| D19 | Line items, variants, Monday column raw values, Meta `actions` arrays stay in `attributes`/raw, not columns. | R9. No SB panel reads them. |
| D20 | Google access tokens (1 h) are refreshed by the worker's `refreshTokens` step when `expires_at < now() + 10 min`, under a row lock; a run whose token is already expired calls the same routine before its first request. Shopify custom-app, Monday personal, and Meta system-user tokens do not expire and have no refresh. R30's "24 h" is read as "a refresh never waits more than one tick". | Only Google has a refresh flow among SB's sources. A 24-hour lookahead against a 1-hour token would refresh on every tick (288×/day) and, under refresh-token rotation, race itself into `invalid_grant`. |
| D21 | R1's "every table has a policy" is read as: every table has RLS **enabled + forced**, and every table **granted to `authenticated`** has a policy whose qual is exactly `client_id = (select data.active_client_id())` (`id = …` on `clients`). Tables with no grant (`raw*`, `source_tokens`, `connector_schedule`, `connector_runs`, `notifications`, `worker_leases`, `download_tickets`, `raw_latest`) have no policy. | No grant is a stronger deny than a policy; CI asserts the exact qual, not a substring. |
| D22 | Every `data`/`api` object is owned by `postgres` (Supabase's `BYPASSRLS` role). Security-definer helpers and RPCs work under `force row level security` only because of that attribute. | Stated so the migration role is never swapped for one without `BYPASSRLS`; CI asserts `pg_roles.rolbypassrls` for the owner. |
| D23 | Housekeeping steps (partitions, token refresh, health, alerts, thumbnails, renormalize, purge, pooled egress) run under a row lease in `data.worker_leases`; only one execution holds it. The claim step needs no lease (SKIP LOCKED). Cloud Run Job `taskCount = N` shards the claim by `hashtext(client_id::text) % N`. | Overlapping executions are allowed, so every non-idempotent step needs its own mutex. Row leases work through the transaction-mode pooler; session advisory locks do not. |
| D24 | An original is readable only with a **download ticket**: `api.download_url` charges the ledger, then inserts `data.download_tickets(client_id, storage_path, expires_at = now() + 5 min)`; the Storage SELECT policy on `orig/` requires a live ticket. Budget is checked **before** charging (`used >= quota` → `BCNS1`), so one download may cross the line and the next is denied. | Without the ticket a dashboard can call `createSignedUrl` directly and download unmetered; with charge-after-check the ledger can never exceed the quota and the deny never fires. |
| D25 | `daily_metrics` stores no all-zero rows (an insight row with `spend = impressions = clicks = 0` is skipped) and ad-level rows are kept unbounded; the metric registry is a lookup table `data.metric_defs`, not a `CHECK`. Ceiling: ~10⁸ rows on one Pro instance; past it, partition by `hashtext(client_id)`. | Meta returns rows only for ads with delivery, so ad-level volume tracks active ads, not the ad catalogue. A `CHECK` registry needs an `ACCESS EXCLUSIVE` validation scan on the biggest table for every new metric. |

## 1. Schema `data` — tables

DDL sketch per table: columns, keys, indexes. `…common…` on canonical tables means:

```sql
id                uuid primary key default gen_random_uuid(),
client_id         uuid not null references data.clients(id),
source            data.source not null,
external_id       text not null,
attributes        jsonb not null default '{}'::jsonb,
source_updated_at timestamptz,
created_at        timestamptz not null default now(),
updated_at        timestamptz not null default now(),   -- trigger data.touch_updated_at()
unique (client_id, source, external_id)
```

Types:

```sql
create schema data;  create schema api;
create extension if not exists btree_gin;
create type data.source        as enum ('shopify','meta','monday','meet','upload','dashboard','platform','drive');
create type data.client_status as enum ('active','paused','churned');
create type data.member_role   as enum ('member','owner');
create type data.token_kind    as enum ('shopify_admin','monday_personal','meta_system_user','google_oauth_refresh');
create type data.token_status  as enum ('active','auth_failed','revoked');
create type data.run_mode      as enum ('backfill','incremental','renormalize');
create type data.run_status    as enum ('running','ok','error','auth_failed');
create type data.health_status as enum ('ok','stale','auth_failed','error','never_ran');
```
`never_ran` is the fifth health value: a schedule row exists but no run has finished. It renders as
"connecting…" and never alerts. It is additive to the REQUIREMENTS enum.

### 1.1 Tenancy

**`data.clients`**
```sql
id                  uuid primary key default gen_random_uuid(),
slug                text not null unique check (slug ~ '^[a-z0-9-]{2,40}$'),
name                text not null,
status              data.client_status not null default 'active',
timezone            text not null default 'America/New_York',   -- validated by trigger (a subquery CHECK is illegal)
egress_quota_bytes  bigint not null default 21474836480,    -- 20 GiB
churned_at          timestamptz,
notes               text,
created_at / updated_at
```
Trigger `data.clients_timezone_valid`: `before insert or update of timezone` → `perform now() at time zone
new.timezone` inside `begin … exception when others then raise 'BCNS3' end` (an unknown zone name
raises). Trigger `data.clients_timezone_changed`: after update of `timezone` → `update data.connector_schedule
set renormalize_requested_at = now() where client_id = new.id` (R10). Trigger
`data.clients_status_changed`: after update of `status` to `churned` → set `churned_at = now()`.

**`data.memberships`**
```sql
user_id     uuid primary key references auth.users(id) on delete cascade,   -- PK ⇒ one client per user (R3)
client_id   uuid not null references data.clients(id) on delete cascade,
role        data.member_role not null default 'member',
is_smoke    boolean not null default false,       -- the CI smoke user (R39)
created_at  timestamptz not null default now()
```
Index `(client_id)`. Exactly one `is_smoke` row per client is a convention checked by the onboarding
script, not a constraint.

**`data.source_tokens`** — service role only (D13).
```sql
client_id         uuid not null references data.clients(id) on delete cascade,
source            data.source not null,
kind              data.token_kind not null,

refresh_secret    text,
expires_at        timestamptz,

status            data.token_status not null default 'active',
status_detail     text,
attributes        jsonb not null default '{}',   -- per-token non-refresh secrets, e.g. Google oauth_client_secret (§4.5)
created_at / updated_at,
primary key (client_id, source)
```

**`data.dashboard_versions`**
```sql
client_id    uuid primary key references data.clients(id) on delete cascade,
api_version  text not null,          -- 'v1'
app_version  text not null,          -- dashboard package.json version
reported_at  timestamptz not null default now()
```

**`data.connector_runs`** — one row per worker run; pruned after 90 days.

**`data.connector_health`** — written by the health job (D6); read by `api.connector_health_v1`.

```sql
source           data.source not null,
```

**`data.notifications`** — bcns alert log + dedupe.

```sql
last_error  text
```
Index `(created_at) where sent_at is null` (retry queue, §5.6).

**`data.egress_ledger`**

### 1.3 Raw

**`data.raw`** — partitioned by range on `fetched_at`, one partition per calendar month
(`data.raw_2026_09`, …). **No default partition**: a missing month is a loud insert error, never a
silent trap that blocks later partition creation. Created by `data.ensure_raw_partitions()` (§1.5).
```sql
client_id          uuid not null,
source             data.source not null,
entity             text not null,          -- 'order','refund','payout','product','inventory_snapshot',
                                           -- 'campaign','ad','insight_campaign_day','insight_ad_day',
                                           -- 'board','item','drive_file','doc'
external_id        text not null,
fetched_at         timestamptz not null default now(),
source_updated_at  timestamptz,
run_id             bigint,                 -- connector_runs.id (no FK: partitions + pruning)
payload_hash       text not null,          -- md5 of payload::text (jsonb canonical form)
payload            jsonb not null,
primary key (client_id, source, entity, external_id, fetched_at)
) partition by range (fetched_at);
```
Index per partition (inherited): `(client_id, source, entity, fetched_at)`. No FK to `clients`
(partition pruning + hard-delete script handles it). Retention: forever while
`clients.status <> churned` (dedupe below keeps "forever" to changes only).

**`data.raw_latest`** — un-partitioned pointer to the newest raw row per key (D5).
```sql
client_id     uuid not null,
source        data.source not null,
entity        text not null,
external_id   text not null,
payload_hash  text not null,
fetched_at    timestamptz not null,
primary key (client_id, source, entity, external_id)
```
Raw write per page, one statement pair inside the page transaction:
```sql
-- 1. keys whose hash changed (or are new)
with incoming(client_id, source, entity, external_id, source_updated_at, payload_hash, payload) as (values …),
changed as (
  insert into data.raw_latest as l (client_id, source, entity, external_id, payload_hash, fetched_at)
  select client_id, source, entity, external_id, payload_hash, now() from incoming
  on conflict (client_id, source, entity, external_id) do update
    set payload_hash = excluded.payload_hash, fetched_at = excluded.fetched_at
    where l.payload_hash is distinct from excluded.payload_hash
  returning client_id, source, entity, external_id)
-- 2. append only those
insert into data.raw (client_id, source, entity, external_id, fetched_at, source_updated_at, run_id, payload_hash, payload)
select i.client_id, i.source, i.entity, i.external_id, now(), i.source_updated_at, $run_id, i.payload_hash, i.payload
from incoming i join changed using (client_id, source, entity, external_id);
```
Normalize still runs over the **whole page** (canonical upsert is idempotent), so an unchanged
payload costs one `raw_latest` lookup and no raw row.

### 1.4 Canonical

All eight carry `…common…` (§1 top) and the index `(client_id, updated_at)` for dashboard caching.

**`data.customers`** — `email text`, `name text`, `first_order_at timestamptz`, `orders_count int`,
`total_spent_minor bigint`, `currency char(3)`. Index `(client_id, email)`.

**`data.jobs`** — `kind text not null default 'task'`, `title text not null`, `status text`,
`is_done boolean not null default false`, `priority text`, `group_name text`, `owner text`,
`due_on date`, `url text`, `deleted_at timestamptz`. Indexes `(client_id, is_done, due_on)`,
`(client_id, source_updated_at desc) where is_done` (activity feed branch).

**`data.messages`** — `kind text not null` ('meeting_note'), `title text`, `body text`,
`occurred_at timestamptz not null`, `participants text[]`, `url text`.
Index `(client_id, kind, occurred_at desc)`.

**`data.money`** — `kind text not null` ('order' | 'refund' | 'payout'), `occurred_at timestamptz
not null`, `day date not null` (client-local), `amount_minor bigint not null` (refunds negative),
`currency char(3) not null`, `status text`, `order_number text`, `customer_external_id text`,
`items_count int`, `url text`. Indexes `(client_id, day)`, `(client_id, kind, occurred_at desc)`,
`(client_id, occurred_at desc)` (activity feed branch).
Check: `kind in ('order','refund','payout')`.

**`data.media`** — `kind text not null` ('image' | 'video' | 'file'), `storage_path text`
(`<client_id>/orig/<uuid>.<ext>`; null until the Meta download lands), `thumb_path text`,
`filename text not null`, `mime text`, `bytes bigint`, `width int`, `height int`,
`title text`, `tags text[] not null default '{}'`, `uploaded_by uuid references auth.users(id)`,
`thumb_error text` (set by the thumbnail job; never written by a connector), `deleted_at timestamptz`,
`purge_after timestamptz` (= `deleted_at + 30 days`).
`external_id` = storage path for uploads, `image_hash` for Meta. Indexes: `(client_id, source, deleted_at,
created_at desc)`, `using gin (client_id, tags)` (needs `btree_gin`), and two cross-tenant queue indexes
(D12): `(purge_after) where deleted_at is not null`, `(created_at) where thumb_path is null and kind = 'image'
and deleted_at is null and storage_path is not null and thumb_error is null`.

**`data.media_sets`** — `id uuid pk`, `client_id`, `name text not null`, `description text`,
`created_by uuid`, `created_at/updated_at`, `unique (client_id, name)`.

**`data.media_set_items`** — `client_id uuid not null`, `set_id uuid references data.media_sets(id) on
delete cascade`, `media_id uuid references data.media(id) on delete cascade`, `added_at`,
`primary key (client_id, set_id, media_id)`; index `(client_id, media_id)`.

**`data.products`** — `title text not null`, `handle text`, `status text`, `vendor text`,
`product_type text`, `price_minor bigint`, `currency char(3)`, `inventory_quantity int`,
`variants_count int`, `image_url text`, `url text`. Variants in `attributes.variants[]`.

**`data.daily_metrics`** — no surrogate id.
```sql
client_id    uuid not null references data.clients(id),
source       data.source not null,
day          date not null,
entity_kind  text not null,     -- 'store' | 'campaign' | 'ad'
entity_id    text not null,     -- 'store' | campaign_id | ad_id
metric       text not null,     -- see metric registry below
value        numeric not null,
currency     char(3),           -- set only for money-valued metrics (values are minor units)
updated_at   timestamptz not null default now(),
primary key (client_id, source, day, entity_kind, entity_id, metric)
```
Index `(client_id, day)`, `(client_id, entity_kind, entity_id, day)`. `metric references
data.metric_defs(name)`.

**`data.metric_defs`** — `name text primary key, unit text not null check (unit in ('count','minor','ratio'))`.
Seeded: `sessions count, conversion_rate ratio, inventory_units count, spend minor, impressions count,
clicks count, reach count, purchases count, purchase_value minor`. Adding a metric = one insert (D25).
`cpc`, `ctr`, `roas` are **not** metrics; views compute them. `spend`, `purchase_value` carry `currency`.
Rows whose every metric for the day is zero are not written (D25).

**`data.records`** — `kind text not null check (kind ~ '^[a-z_]{1,64}$')`, `title text`,
`body text`, `occurred_at timestamptz not null default now()`, `deleted_at timestamptz`.
Kinds in use: `campaign`, `ad` (source `meta`); `briefing`, `daily_financial_report` (source
`dashboard`). Index `(client_id, kind, occurred_at desc)`.

### 1.5 Common triggers and helpers

- `data.touch_updated_at()` — `before update` on every table with `updated_at`.
- `data.local_day(ts timestamptz, client uuid) returns date` — `(ts at time zone
  (select timezone from data.clients where id = client))::date`; STABLE. Used by normalize (the
  worker computes `day` itself for bulk inserts; the function is for `renormalize` SQL). Not
  executable by `authenticated` (§2.3 function-privilege default).
- `data.ensure_raw_partitions()` — `create table if not exists data.raw_YYYY_MM partition of data.raw
  for values from (…) to (…)` for the current month through month+2, under
  `pg_advisory_xact_lock(hashtext('raw_partitions'))`. Run **once per day** by the housekeeping lease
  holder (§5.2), never per tick: `CREATE TABLE … PARTITION OF` takes `ACCESS EXCLUSIVE` on `raw`.
- `data.worker_leases` acquire/release — §1.2.

## 2. Access control

### 2.1 Auth hook (JWT claims)

`public.custom_access_token_hook(event jsonb) returns jsonb` — registered in Supabase Auth →
Hooks → "Customize Access Token". Runs on every token issue/refresh.

```sql
create or replace function public.custom_access_token_hook(event jsonb) returns jsonb
language plpgsql stable security definer set search_path = '' as $$
declare rec record; claims jsonb := event->'claims';   -- variable name ≠ any table alias (plpgsql ambiguity)
begin
  select mem.client_id, mem.role, c.status into rec
  from data.memberships mem join data.clients c on c.id = mem.client_id
  where mem.user_id = (event->>'user_id')::uuid;
  if rec is null then
    return jsonb_build_object('error', jsonb_build_object('http_code', 403, 'message', 'no membership'));
  end if;
  if rec.status <> 'active' then
    return jsonb_build_object('error', jsonb_build_object('http_code', 403, 'message', 'client ' || rec.status));
  end if;
  claims := claims || jsonb_build_object('client_id', rec.client_id, 'client_role', rec.role);
  return jsonb_set(event, '{claims}', claims);
end $$;
grant usage on schema public, data to supabase_auth_admin;
grant execute on function public.custom_access_token_hook to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook from authenticated, anon, public;
grant select on data.memberships, data.clients to supabase_auth_admin;
-- RLS policies "auth_admin_read" on both tables: to supabase_auth_admin using (true)
```
Denying the token (403) is what disables logins at churn (R34) and on membership removal, at the
next refresh. **JWT expiry is set to 600 s** (Auth → Sessions) so "next refresh" is ≤ 10 min. The
per-request lockout (R4) comes from the policy functions in §2.2, which do not depend on the token —
for the role as well as the tenant (`active_client_role()` re-reads `memberships`). CI mints a token
**through the hook** (`hook_mints_claims`, §7), not only service-minted JWTs.

### 2.2 Policy helpers (schema `data`, not exposed)

```sql
create function data.jwt_client_id() returns uuid language sql stable as $$
  select nullif(current_setting('request.jwt.claims', true)::jsonb ->> 'client_id', '')::uuid $$;
-- jwt_client_role() is informational only (dashboard UI hints); NO policy or RPC trusts it.
create function data.jwt_client_role() returns data.member_role language sql stable as $$
  select nullif(current_setting('request.jwt.claims', true)::jsonb ->> 'client_role', '')::data.member_role $$;

-- The tenant boundary. NULL ⇒ every policy is false ⇒ zero rows.
create function data.active_client_id() returns uuid
language sql stable security definer set search_path = '' as $$
  select m.client_id
  from data.memberships m join data.clients c on c.id = m.client_id
  where m.user_id = auth.uid()
    and m.client_id = data.jwt_client_id()
    and c.status = 'active' $$;
-- The live role, read from the table every statement (not the claim): demotion takes effect next request.
create function data.active_client_role() returns data.member_role
language sql stable security definer set search_path = '' as $$
  select m.role from data.memberships m join data.clients c on c.id = m.client_id
  where m.user_id = auth.uid() and m.client_id = data.jwt_client_id() and c.status = 'active' $$;

-- No argument: the caller can only ask about its own tenant (no enumeration oracle).
create function data.egress_exceeded() returns boolean
language sql stable security definer set search_path = '' as $$
  select coalesce(e.bytes, 0) >= c.egress_quota_bytes
  from data.clients c
  left join data.egress_ledger e
    on e.client_id = c.id and e.month = date_trunc('month', now() at time zone c.timezone)::date
  where c.id = data.active_client_id() $$;

-- True when api.download_url issued a live ticket for this object to this tenant (D24).
create function data.has_download_ticket(object_name text) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from data.download_tickets t
                 where t.client_id = data.active_client_id()
                   and t.storage_path = object_name and t.expires_at > now()) $$;

revoke execute on function data.active_client_id, data.active_client_role, data.egress_exceeded,
  data.has_download_ticket from public, anon;
grant execute on function data.active_client_id, data.active_client_role, data.egress_exceeded,
  data.has_download_ticket to authenticated;
```
These four are the **only** `data` functions executable by `authenticated` (§2.3).
Every policy below writes the call as `(select data.active_client_id())` — the subselect makes
Postgres evaluate it once per statement (InitPlan) instead of once per row.

### 2.3 Grants

```sql
revoke all on schema public from anon, authenticated;              -- nothing lives there but the hook
grant usage on schema data to authenticated;                        -- needed by security_invoker views
grant usage on schema api  to authenticated, anon;                  -- anon gets USAGE only, no objects
grant select on data.clients, data.memberships, data.dashboard_versions, data.egress_ledger,
                data.connector_health, data.customers, data.jobs, data.messages, data.money,
                data.media, data.media_sets, data.media_set_items, data.products,
                data.daily_metrics, data.records to authenticated;
-- NO grant to authenticated/anon on: data.source_tokens, data.connector_schedule,
--   data.connector_runs, data.notifications, data.raw (and partitions).
-- No INSERT/UPDATE/DELETE grants on any data table to authenticated: writes go through
--   security definer RPCs (§3.3).
alter default privileges in schema data revoke all on tables from anon, authenticated;
-- Functions default to EXECUTE for PUBLIC: close that for every current and future helper.
alter default privileges in schema data revoke execute on functions from public, anon, authenticated;
alter default privileges in schema api  revoke execute on functions from public, anon, authenticated;
revoke execute on all functions in schema data from public, anon, authenticated;
revoke execute on all functions in schema api  from public, anon, authenticated;
-- then the explicit grants: §2.2 helpers (4) and §3.3 RPCs, each `to authenticated`.
```
**Ownership.** Every object in `data` and `api` is owned by `postgres`, which on Supabase carries
`BYPASSRLS` (D22). That is what lets `security definer` helpers read `memberships` and RPCs insert
into tables that have no INSERT policy under `force row level security`. Migrations run as
`postgres`; CI asserts the owner role has `rolbypassrls` (`owner_bypassrls`, §7). Local
`supabase start` matches production here (its `postgres` also has the attribute).
PostgREST config (Dashboard → API): **Exposed schemas = `api`**; Extra search path = `api`.
`public` and `graphql_public` are removed. The GraphQL endpoint is disabled.

### 2.4 RLS policies — one block per table

`alter table … enable row level security; alter table … force row level security;` on **every**
table in `data` (including `raw` partitions, `source_tokens`, `connector_schedule`,
`connector_runs`, `notifications` — those have no policies, so only the service role, which
bypasses RLS, can touch them). CI test `rls_every_table` (§7) fails otherwise.

Shorthand: `T` = `(select data.active_client_id())`, `W` = `(select data.active_client_role()) in ('member','owner')`
(a live table read, not the claim — D2 applies to the role too).

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `clients` | `id = T` | — | — | — |
| `memberships` | `client_id = T` | — | — | — (owner removal via RPC) |
| `dashboard_versions` | `client_id = T` | — (RPC) | — (RPC) | — |
| `egress_ledger` | `client_id = T` | — | — | — |
| `connector_health` | `client_id = T` | — | — | — |
| `customers`, `jobs`, `messages`, `money`, `products`, `daily_metrics` | `client_id = T` | — | — | — |
| `records` | `client_id = T and deleted_at is null` | — (RPC) | — (RPC) | — |
| `media` | `client_id = T` (deleted rows visible for "recently deleted") | — (RPC) | — (RPC) | — |
| `media_sets`, `media_set_items` | `client_id = T` | — (RPC) | — (RPC) | — (RPC) |
| `source_tokens`, `connector_schedule`, `connector_runs`, `notifications`, `raw*`, `raw_latest`, `worker_leases`, `download_tickets`, `metric_defs` | none | none | none | none |

Policies for `supabase_auth_admin` on `memberships` and `clients`: `using (true)` (hook reads).
Every policy is `to authenticated` — `anon` matches nothing.

Writes are all RPC (§3.3): the RPCs are `security definer`, owned by `postgres`, and set
`client_id := data.active_client_id()` themselves (R16). No dashboard statement ever inserts into a
`data` table directly, so no INSERT/UPDATE/DELETE policy is needed for `authenticated`. The corollary:
**RLS is no backstop for RPC writes** — every statement inside a write RPC carries
`client_id = tenant` explicitly (§3.3 rule 1), and CI exercises every RPC cross-tenant by
enumerating `pg_proc` (§7 `rpc_every_write_scoped`).

### 2.5 Storage

Bucket `media`, private, `file_size_limit = 104857600` (100 MB, R20), `allowed_mime_types = null`
(any type; the upload RPC records the mime). Object key layout, all under the tenant prefix:

```
<client_id>/orig/<media_uuid>.<ext>      originals (uploads and Meta creative copies)
<client_id>/thumb/<media_uuid>.jpg       thumbnails, written only by the worker
```

Policies on `storage.objects` (`P1` = `(storage.foldername(name))[1]`, `P2` = `…[2]`):

```sql
-- read originals: tenant match AND a live download ticket from api.download_url (R19, R22, D24)
create policy media_read_orig on storage.objects for select to authenticated using (
  bucket_id = 'media' and P1 = (select data.active_client_id())::text and P2 = 'orig'
  and data.has_download_ticket(name));
-- read thumbnails: tenant match only, no budget (R21)
create policy media_read_thumb on storage.objects for select to authenticated using (
  bucket_id = 'media' and P1 = (select data.active_client_id())::text and P2 = 'thumb');
-- upload originals: tenant prefix, member/owner, orig folder only
create policy media_insert on storage.objects for insert to authenticated with check (
  bucket_id = 'media' and P1 = (select data.active_client_id())::text and P2 = 'orig'
  and (select data.active_client_role()) in ('member','owner'));
-- no UPDATE/DELETE for authenticated: deletes are soft (RPC) and purged by the worker.
```
The dashboard uploads with `supabase.storage.from('media').upload('<client_id>/orig/<uuid>.<ext>', file)`
then calls `api.register_upload(path, …)`. Signed URLs for originals come from
`createSignedUrl(path, 300)` **after** `api.download_url` (D9/D24): without the ticket the policy
denies and `createSignedUrl` returns 400/404, so a dashboard cannot skip the meter. Thumbnails are
read with `createSignedUrl` too (or `createSignedUrls` in batches of 100) — never public, never ticketed.

## 3. Schema `api` — the dashboard contract

### 3.1 Rules

- Every view: `create view api.<name>_v1 with (security_invoker = true) as …`; exposes
  `client_id`, `source`, `updated_at`; `grant select on api.<name>_v1 to authenticated`.
- Additive only. A column is never removed or retyped in `_v1`; breaking changes are `_v2`.
  CI `api_columns_additive` (§7) diffs `information_schema.columns` for `api` against the committed
  `api/contract.json` snapshot.
- Views expose `client_id` so the dashboard can cache-key by it; RLS guarantees it equals the
  caller's tenant.
- Money columns are `*_minor bigint` + `currency`. Ratios (`roas`, `conversion_rate`, `aov_minor`)
  are computed in views so every dashboard shows the same number.

### 3.2 Views

**`api.client_v1`** — `client_id (= clients.id), source ('platform'), name, slug, timezone, status,
egress_quota_bytes, updated_at`. One row.

**`api.money_v1`** — every `data.money` column: `id, client_id, source, external_id, kind,
occurred_at, day, amount_minor, currency, status, order_number, customer_external_id, items_count,
url, attributes, source_updated_at, updated_at`.

**`api.daily_metrics_v1`** — `client_id, source, day, entity_kind, entity_id, metric, value,
currency, updated_at`.

**`api.daily_summary_v1`** — one row per `(client_id, day)`; the Overview / Shopify panel / DFR
source. `source = 'platform'`.
```sql
with days as (select client_id, day from data.money union select client_id, day from data.daily_metrics),
m as (select client_id, day,
        sum(amount_minor) filter (where kind = 'order')  as revenue_minor,
        count(*)          filter (where kind = 'order')  as orders,
        sum(amount_minor) filter (where kind = 'refund') as refunds_minor,
        sum(amount_minor) filter (where kind = 'payout') as payouts_minor,
        max(currency) as currency,
        max(updated_at) as m_upd
      from data.money group by 1, 2),
d as (select client_id, day,
        sum(value) filter (where metric = 'sessions')                        as sessions,
        max(value) filter (where metric = 'conversion_rate')                 as conversion_rate_src,
        max(value) filter (where metric = 'inventory_units')                 as inventory_units,
        sum(value) filter (where metric = 'spend'          and source = 'meta') as ad_spend_minor,
        sum(value) filter (where metric = 'purchase_value' and source = 'meta') as ad_purchase_value_minor,
        sum(value) filter (where metric = 'impressions'    and source = 'meta') as ad_impressions,
        sum(value) filter (where metric = 'clicks'         and source = 'meta') as ad_clicks,
        sum(value) filter (where metric = 'purchases'      and source = 'meta') as ad_purchases,
        max(currency) filter (where metric = 'spend'       and source = 'meta') as ad_currency,
        max(updated_at) as d_upd
      from data.daily_metrics where entity_kind in ('store','campaign') group by 1, 2)
select days.client_id, 'platform'::data.source as source, days.day,
       coalesce(m.revenue_minor,0) as revenue_minor, coalesce(m.orders,0) as orders,
       coalesce(m.refunds_minor,0) as refunds_minor, coalesce(m.payouts_minor,0) as payouts_minor,
       m.currency,
       case when coalesce(m.orders,0) > 0 then round(m.revenue_minor::numeric / m.orders) end as aov_minor,
       d.sessions, d.inventory_units,
       coalesce(d.conversion_rate_src,
                case when d.sessions > 0 then m.orders::numeric / d.sessions end) as conversion_rate,
       d.ad_spend_minor, d.ad_purchase_value_minor, d.ad_currency, d.ad_impressions, d.ad_clicks, d.ad_purchases,
       case when d.ad_spend_minor > 0 then round(d.ad_purchase_value_minor / d.ad_spend_minor, 4) end as roas,
       greatest(coalesce(m.m_upd, '-infinity'), coalesce(d.d_upd, '-infinity')) as updated_at
from days left join m using (client_id, day) left join d using (client_id, day);
```
No outer aggregate: `m` and `d` are already one row per `(client_id, day)`. `ad_currency` is the
ad account's billing currency and may differ from `currency` (store); the dashboard labels each.
Only `campaign`-level Meta rows feed the totals (ad-level rows would double count).
`conversion_rate` prefers a source-reported value (`metric = 'conversion_rate'`) and falls back
to `orders ÷ sessions`; if neither exists it is null and the tile renders "—" (see §11).

**`api.campaign_daily_v1`** — one row per `(client_id, day, campaign_id)`: `client_id, source
('meta'), day, campaign_id (= entity_id), campaign_name, campaign_status, objective, spend_minor,

### 3.3 RPCs

All: `language plpgsql security definer set search_path = ''`, owned by `postgres`,
`revoke execute … from public, anon; grant execute … to authenticated`. Each begins with
`tenant := data.active_client_id(); if tenant is null then raise … 'BCNS0'`. Input is validated
before any write. Three rules with no exceptions:

1. **Every** `select`/`update`/`delete` inside an RPC carries `client_id = tenant` (for `memberships`:
   `client_id = tenant` on the target row; for `media_set_items`: on the set **and** the media). An id
   argument that matches no tenant row → `BCNS4` (single-id RPCs) or is ignored (array RPCs). RLS is
   not a backstop for these functions (§2.4), so CI enumerates `pg_proc` and calls each RPC with a
   cross-tenant id (`rpc_every_write_scoped`, §7).
2. `W` (write role) and `owner` are read from `data.active_client_role()`, never the JWT claim.
3. A raise anywhere rolls back the whole RPC statement (PostgREST wraps one call in one transaction);
   no savepoints.

Errors use custom SQLSTATEs so the dashboard can branch on `error.code`:

| SQLSTATE | name | meaning |
|---|---|---|
| `BCNS0` | `no_tenant` | no active membership / claim |
| `BCNS1` | `budget_reached` | monthly egress quota exceeded (R22) |
| `BCNS2` | `forbidden_role` | needs `owner` |
| `BCNS3` | `validation` | bad argument (detail names the field) |
| `BCNS4` | `not_found` | id not in tenant |
| `BCNS5` | `too_large` | file > 100 MB or attributes > 256 KB |

PostgREST returns these as HTTP 400 with `{code, message, details, hint}`.

## 4. Connectors

### 4.1 Module contract (R24)

One TypeScript module per source in `worker/connectors/<source>.ts`:

```ts
export interface Connector {
  source: Source;                                       // 'shopify' | 'meta' | 'monday' | 'meet' | 'drive'
  defaults: { interval: string; backfillDepth: string;  // Postgres interval literals
              rateLimit: { concurrency: number; minDelayMs: number };   // per (source, client_id) — never global
              fullList?: { entity: string; table: 'jobs' | 'records' | 'media' }[] }; // entities whose complete pull authorises tombstones
  configSchema: ZodSchema;                              // shape of connector_schedule.config
  tokenKind: TokenKind;
  backfill(ctx: RunContext, from: Date, cursor: Json|null): AsyncIterable<Page>;
  incremental(ctx: RunContext, cursors: Record<string, Json>): AsyncIterable<Page>; // per-entity watermarks
  refreshToken?(ctx: RunContext): Promise<{ secret: string; expiresAt: Date }>;
  normalize(ctx: RunContext, rows: RawRow[]): CanonicalWrites;          // pure: raw → canonical, no ids from the DB
}
interface Page { raw: RawRow[]; entity: string; cursor: Json; entityDone: boolean; done: boolean }
  // cursor = position within `entity`; persisted after each page into incremental_cursor[entity]
  // (incremental) or backfill_cursor (backfill) — only when entityDone, for incremental watermarks.
interface RawRow { entity: string; externalId: string; sourceUpdatedAt?: Date; payload: Json }
interface CanonicalWrites { money?: MoneyRow[]; products?: …; jobs?: …; messages?: …;
                            media?: MediaRow[]; dailyMetrics?: MetricRow[]; records?: RecordRow[]; customers?: … }
```
**Tombstones are the worker's job, not the connector's.** For each `fullList` entity the worker
accumulates every `externalId` it saw during the run; when the run ends with `done: true` (not a
budget stop, not an error) it sets `deleted_at = now()` on tenant rows of `table` for that `source`
whose `external_id` is not in the set, and clears `deleted_at` on any that reappeared. A partial run
never tombstones. `normalize` cannot produce a DB-generated id; cross-entity references use source
keys (`image_hash`, `campaign_id`), and views join on those.
`RunContext` gives the connector its token, `config`, `clients.timezone`, an HTTP client with the
source's rate limiter, and a logger. It has no scheduler, no DB handle, no Storage handle except
`ctx.putObject(path, bytes, mime)` for media copies. The worker (§5) drives the iterator, writes
raw, calls `normalize` on each page, upserts, persists the cursor.

Idempotency across all connectors: raw insert is hash-deduped (§1.3); canonical upsert on
`(client_id, source, external_id)` sets every mapped column (`attributes` replaced, not merged —
which is why worker-owned state such as `media.thumb_error` lives in its own column);
`daily_metrics` upsert on its PK sets `value`. Running the same page twice changes nothing (R7/R8).

**Incremental cursors are per entity.** `connector_schedule.incremental_cursor` is
`{ "<entity>": <watermark> }`; the worker writes `incremental_cursor[entity]` only when a page
reports `entityDone`, so a run cut off by the budget after `order` but before `product` leaves the
`product` watermark untouched and the next run fetches those products. Backfill cursors are one
object per connector (documented in each section) and persisted every page.

## 5. Worker and jobs

### 5.1 Runtime

One Node 22 container, `worker/`, image built by GitHub Actions and deployed as **Cloud Run Job
`bcns-data-worker`** in the existing bcns GCP project. **Cloud Scheduler** `bcns-data-tick` runs
`*/5 * * * *` → `POST …/jobs/bcns-data-worker:run`. Job settings: `taskCount = TASK_COUNT`
(default **2**), `parallelism = taskCount`, task timeout 600 s, max retries 0, 1 vCPU / 1 GiB
(sharp), overlapping executions **allowed** (claim leases + `worker_leases` make every step safe).
Each task reads `CLOUD_RUN_TASK_INDEX` and claims only rows where
`hashtext(client_id::text) % TASK_COUNT = index`; task 0 alone runs housekeeping (§5.2).
Env: `DATABASE_URL` (Supabase pooler, **transaction mode**, `pg` pool `max = 4` per task —
session mode would hold real backends against the same budget PostgREST serves 1,000 dashboards
from), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `BCNS_ALERT_EMAIL`,
`EGRESS_ALLOWANCE_BYTES` (default 268435456000), `RUN_BUDGET_MS` (default 240000), `CLAIM_LIMIT`
(default **24** per task), `TASK_COUNT`. The worker talks to Postgres directly (`pg`), not through
PostgREST; the service key is used only for Storage. Nothing relies on session state (no
`LISTEN`, no session advisory locks, no prepared statements across transactions).

**Throughput.** Claimed rows run concurrently (per-account semaphores, `p-limit(CLAIM_LIMIT)`), so
one tick's ceiling is `TASK_COUNT × CLAIM_LIMIT` runs of ≤ `RUN_BUDGET_MS` each inside the 600 s
task timeout. Capacity/day = `TASK_COUNT × CLAIM_LIMIT × 288`:

| clients | demand runs/day (3 hourly + 1 six-hourly source) | TASK_COUNT × CLAIM_LIMIT | capacity/day |
|---|---|---|---|
| 50 (year 1) | 3,800 | 2 × 24 | 13,824 |
| 250 | 19,000 | 4 × 24 | 27,648 |
| 1,000 | 76,000 | 12 × 24 | 82,944 |

`TASK_COUNT` is the only knob; Cloud Run Jobs allow up to 10,000 tasks. Intervals are per-client
overrides (`connector_schedule.interval`), so a quiet client can be slowed instead. Backfills use
spare slots only (§5.3), so onboarding never delays incremental runs. Re-check this table when
`TASK_COUNT` reaches 8: that is the point to revisit pg-boss (REQUIREMENTS "Still open").

Entry `tick()` runs the steps below in order; each step is wrapped so a failure in one is logged
and the next still runs. Total wall clock ≤ 600 s.

### 5.2 Step order

Steps 0 and 3 run in every task. Steps 1–2 and 4–9 run only in task 0 **and** only after
acquiring `worker_leases('housekeeping')` with a 9-minute TTL (D23); if another execution holds it,
task 0 skips them (they are all retried next tick). Step 7 takes its own per-client lease.

| # | step | what |
|---|---|---|
| 0 | `reap` | `update connector_runs set status='error', error='lease expired', finished_at=now() where status='running' and started_at < now() − 20 min`; `update connector_schedule set lease_until = null where lease_until < now()` |
| 1 | `ensurePartitions` | `select data.ensure_raw_partitions()` — once per day (skip when `raw_YYYY_MM` for month+2 exists) |
| 2 | `refreshTokens` + `probeAuthFailed` | §5.4 |
| 3 | `claimAndRun` | §5.3 (all tasks, sharded) |
| 4 | `computeHealth` | §5.5 |
| 5 | `alerts` | §5.6 (including the unsent-notification retry) |

### 5.3 Claim and run (R25, R26, R28)

```sql
with due as (
  select s.client_id, s.source
  from data.connector_schedule s
  join data.clients c on c.id = s.client_id
  left join data.source_tokens t on (t.client_id, t.source) = (s.client_id, s.source)
  where s.enabled and c.status = 'active'
    and s.next_run_at <= now()
    and (s.lease_until is null or s.lease_until < now())
    and coalesce(t.status, 'active') = 'active'
    and hashtext(s.client_id::text) % $3 = $4  -- TASK_COUNT, CLOUD_RUN_TASK_INDEX
  order by (s.backfill_cursor is not null), s.next_run_at   -- incremental rows first, backfills fill spare slots
  limit $1                                    -- CLAIM_LIMIT
  for update of s skip locked)
update data.connector_schedule s
set lease_until = now() + interval '8 minutes', lease_owner = $2   -- 2 × RUN_BUDGET_MS
from due where (s.client_id, s.source) = (due.client_id, due.source)
returning s.*;
```
Backfill rows re-arm with `next_run_at = now()` after every budget stop, so without the
`(backfill_cursor is not null)` sort key three onboarding clients would monopolise every slot. With
it, an incremental row is never behind a backfill; backfills take whatever is left.

Claimed rows run concurrently in-process (`p-limit(CLAIM_LIMIT)`), each connector's
`rateLimit.concurrency` enforced by a semaphore keyed **`(source, client_id)`** — a per-account
limit, never a process-wide one, so no client waits on another client's API budget (R26).
Per claimed row:

1. `insert connector_runs (mode = backfill_cursor is not null ? 'backfill' : 'incremental', status 'running')`.
2. Load token + config; build `RunContext`.
3. Iterate `backfill(from, cursor)` or `incremental(since)`. Per page, in one transaction:
   insert raw (`on conflict do nothing`), `normalize`, upsert canonical, apply tombstone if
   present (a `media` tombstone also sets `purge_after = now() + 30 days`, cleared if the id returns), `update connector_schedule set backfill_cursor|incremental_cursor = page.cursor`,
   bump `connector_runs.pages/rows_*`. Stop when `page.done` or `RUN_BUDGET_MS` elapsed.
4. Finish: `status='ok'`, `finished_at`. Schedule: if backfill finished → `backfill_cursor = null`,
   `next_run_at = now()` (first incremental follows immediately), notification
   `backfill_done:<client>:<source>`; if backfill still in progress → `next_run_at = now()`; else
   `next_run_at = now() + interval`. `last_success_at = now()`, `consecutive_failures = 0`,
   `lease_until = null`.
5. On error, classify **by source error body first, HTTP status second**:
   - *throttle* — Shopify GraphQL `errors[].extensions.code = 'THROTTLED'` (HTTP 200), Meta
     `error.code ∈ {4, 17, 32, 613}` or `error.is_transient` (HTTP 400/403), Monday
     `ComplexityException`, Google 403 `rateLimitExceeded`/`userRateLimitExceeded`, any HTTP 429 →
     step 6, never an error.
   - *auth* — Meta `error.code = 190` or `error.type = 'OAuthException'` with subcode 458–467, Google
     `invalid_grant`/401, Shopify HTTP 401 or `errors[].extensions.code = 'ACCESS_DENIED'`, Monday
     `USER_UNAUTHORIZED` → `status = 'auth_failed'`, `source_tokens.status = 'auth_failed'`,
     `status_detail`.
   - *everything else* → `status = 'error'`.
   Then `connector_schedule.last_error = redact(message)` (drop query strings, strip
   `access_token=[^&\s]*`, `shpat_\w+`, `Bearer \S+`, `Authorization`/`X-Shopify-Access-Token`
   header values, cap 300 chars; the untouched text goes to `connector_runs.error`), `last_error_at`,
   `consecutive_failures += 1`, `next_run_at = now() + least(interval, (2 ^ consecutive_failures) *
   interval '1 minute')`, lease cleared. Cursor stays where the last committed page left it.
6. Throttles: sleep per the connector's rule inside the budget; if the budget runs out, treat as a
   normal budget stop, not an error.

A run touches exactly one `(client_id, source)`; nothing it does blocks another row (R26). A tick
that finds nothing due exits in < 2 s.

### 5.4 Token refresh (R30)

`select … from data.source_tokens where status = 'active' and expires_at is not null and expires_at <
now() + interval '10 minutes' for update skip locked` → for each, the connector's `refreshToken()`
inside that transaction; success updates `secret, expires_at, last_refreshed_at`; failure sets
`status = 'auth_failed', status_detail`. Only `google_oauth_refresh` has an `expires_at`; the others
are skipped by the predicate. A 1-hour token is therefore refreshed ~24×/day, never per tick, and
never by two executions at once (D20). A run that finds `expires_at < now()` (the housekeeping lease
was held elsewhere) calls the same locked routine for its own row before its first request.

**`probeAuthFailed`.** `source_tokens where status = 'auth_failed' and updated_at < now() − 1 hour`
→ one cheap authenticated call per source (`shop { id }`, `me?fields=id`, `me { id }`, Drive
`about?fields=user`); success flips `status = 'active'` (a token mis-classified during an outage
recovers within an hour); failure bumps `updated_at` so the probe is hourly, not per tick.

### 5.5 Health (R32)

For every `connector_schedule` row of an active client, compute the status in one SQL statement and
upsert `connector_health` **only where the result is distinct** from the stored row:

| status | rule (evaluated in order) |
|---|---|
| `auth_failed` | `source_tokens.status = 'auth_failed'` or last finished run `status = 'auth_failed'` |
| `never_ran` | no run with `finished_at` |
| `error` | last finished run `status = 'error'` and `consecutive_failures >= 1` and not stale |
| `stale` | `last_success_at < now() − 3 * interval` (missed ≥ 3 runs), **or** — only for sources whose connector declares a `fullList` entity (Monday, Meta, Drive) — the last finished `ok` run fetched 0 rows for that entity while the previous 10 `ok` runs each fetched > 0. Never applied to `updated_at`-filtered incrementals (Shopify, Meet): an idle store legitimately returns 0 rows at night. |
| `ok` | otherwise |

```sql
insert into data.connector_health as h (client_id, source, status, status_since, last_run_at, last_success_at, last_error)
select … from computed
on conflict (client_id, source) do update set
  status = excluded.status,
  status_since = case when h.status = excluded.status then h.status_since else excluded.status_since end,
  last_run_at = excluded.last_run_at, last_success_at = excluded.last_success_at,
  last_error = excluded.last_error, computed_at = now()
where (h.status, h.last_error, h.last_success_at, h.last_run_at)
      is distinct from (excluded.status, excluded.last_error, excluded.last_success_at, excluded.last_run_at);
```
`status_since` therefore changes only on a status transition (so alert dedupe keys built from it are
stable). `last_error` is the redacted `connector_schedule.last_error` when status ∈ {error,
auth_failed, stale}, else null. Paused/churned clients keep their last row; `computeHealth` skips them.

### 5.6 Alerts (R23, R33)

All alerts: `insert into notifications (…, sent_at = null) on conflict (dedupe_key) do nothing`; a
new row means a new alert. Then, for every row `where sent_at is null and attempts < 5`
(new or previously failed), one Resend email to `BCNS_ALERT_EMAIL`, subject prefixed `[bcns-data]`;
success sets `sent_at`, failure sets `attempts += 1, last_error`. A Resend outage delays alerts by
ticks, never loses them; a row at `attempts = 5` is itself surfaced by the `notifications_stuck`
row (`dedupe_key = 'notifications_stuck:<date>'`).

| kind | when | dedupe_key |
|---|---|---|
| `auth_failed` | health row `auth_failed` | `auth_failed:<client>:<source>:<status_since>` |
| `stale` | health row `stale` with `status_since < now() − 6 h` | `stale:<client>:<source>:<status_since::date>` |
| `egress_client_quota` | `egress_exceeded(client)` first true this month | `egress_client:<client>:<month>` |
| `egress_pooled_80` | `sum(egress_ledger.bytes) for the current calendar month ≥ 0.8 * EGRESS_ALLOWANCE_BYTES` | `egress_pooled:<month>` |
| `backfill_done` | §5.3 step 4 | `backfill_done:<client>:<source>` |

### 5.7 Thumbnails (R21)

`select id, client_id, storage_path from data.media where thumb_path is null and kind = 'image' and
deleted_at is null and storage_path is not null and thumb_error is null order by created_at limit 50`
(exactly the §1.4 queue index) → download original with the service key, `sharp().rotate()
.resize({ width: 512, height: 512, fit: 'inside' }).jpeg({ quality: 80 })`, upload to
`<client_id>/thumb/<id>.jpg` with `upsert: true`, set `thumb_path, width, height` (original
dimensions from sharp metadata). Unreadable image → `thumb_error = <message>` (a dedicated column,
so a connector re-upsert cannot clear it and re-queue the file). Videos/files: no thumb; the
dashboard shows a type icon. Runs under the housekeeping lease, so two executions never process the
same batch.

### 5.8 Re-normalize (R7, R10)

Triggered by `connector_schedule.renormalize_requested_at is not null` (timezone change) or by
`scripts/renormalize.ts --client <slug> [--source <s>] [--since <date>]`. Takes
`worker_leases('renormalize:<client_id>')` (TTL 9 min) and a `connector_runs` row with
`mode = 'renormalize'`; it does **not** touch the schedule lease, so incremental runs continue.
Work is driven by `raw_latest` (one row per key, un-partitioned): keyset-paginate
`where (client_id, source) = … and (entity, external_id) > (cursor.entity, cursor.external_id)
order by entity, external_id limit 1000`, fetch each key's newest raw row by
`(client_id, source, entity, external_id, fetched_at)` from `raw_latest.fetched_at` (a PK lookup,
partition-pruned), call `normalize`, upsert, then persist `renormalize_cursor = { entity,
external_id }`. Budget `RENORMALIZE_BUDGET_MS` (default 120000) per tick; resumes from the cursor
next tick. When the keyset is exhausted: `renormalize_requested_at = null, renormalize_cursor =
null`. Only that client's rows are touched.

### 5.9 Purge and orphans

- `media where purge_after < now() limit 200` → delete `orig` + `thumb` objects, delete row
  (cascades set items). Bounded per tick.
- Orphans: `storage.objects o where bucket_id='media' and P2='orig' and created_at < now() − 24 h
  and not exists (select 1 from data.media m where m.storage_path = o.name) limit 200` → delete.
  `NOT EXISTS`, not `NOT IN`: `media.storage_path` is nullable (Meta rows before download), and
  `NOT IN` against a set containing NULL never matches. The 24 h guard protects in-flight uploads.
- `download_tickets where expires_at < now() − 1 hour` → delete.
- `connector_runs where started_at < now() − 90 days limit 5000` → delete.
- `notifications where sent_at < now() − 180 days` → delete.

## 7. Verification design (R1, R2, R13, R14, R19, R39)

Platform CI (`.github/workflows/ci.yml`) starts `supabase start` (local stack), applies
migrations, seeds **two clients** (`acme`, `beta`) with one member each, one owner for `acme`, one
smoke user each, and ~50 rows per canonical table per client plus 3 media objects per client.
Tests run with `vitest` against PostgREST + Storage using the seeded users' JWTs, and against
Postgres as `postgres` for catalog checks.

Seed adds a **third client `gamma` with `status = paused`** (one member) so the liveness tests
have a fixture that is not the one under test.

| test | asserts |
|---|---|
| `rls_every_table` | for every row of `pg_tables where schemaname = 'data'` (partitions included): `rowsecurity = true` **and** `forcerowsecurity = true`; and for every table with any grant to `authenticated` (`information_schema.role_table_grants`), every policy's `pg_get_expr(polqual)` is **exactly** `(client_id = ( SELECT data.active_client_id() AS active_client_id))` (or that `AND` a documented extra predicate listed in the test's allow-map). ## 8. Dashboard template — shared-platform mode (R37, R38)

  returns a typed Supabase client whose `Database` type is generated from schema `api` only
  (`supabase gen types --schema api`). Exposes `views.<name>_v1()` builders, `rpc.<name>()`
  wrappers that map SQLSTATEs to a `DataClientError { code: 'no_tenant' | 'budget_reached' | … }`,
  `media.upload(file, { title, tags })` (Storage upload → `register_upload`),

  and `health()` (`client_v1` read). Nothing else. `@nseluga/app-core` is untouched.
- **Template mode** `DATA_SOURCE=shared` (env; default unset = today's own-project mode): login
  page targets the shared project; `/health` calls `health()`; no `supabase/migrations/`; the
  build fails if `SUPABASE_SERVICE_ROLE_KEY` is set (`scripts/check-env.ts`). With `DATA_SOURCE`
  unset and no env the template builds and serves unchanged (R38).
- Dashboard-side config (per client, dashboard `.env`): `SHOPIFY_ADMIN_URL`, `ADS_MANAGER_URL`,
  `MONDAY_BOARD_URL`, `MEET_URL`, `NOTES_URL`, `REPORT_HOUR` (06:00), `AI_MONTHLY_BUDGET_USD`,
  `RESEND_*`, `SMOKE_EMAIL/PASSWORD` (CI only). None of these is a platform fact.
- Agents sign in as a per-client agent user (`agent+<slug>@bcn-services.com`, role member, minted
  by `add-member --agent`) through `signIn`; `agentTools()/runTool` expose read views (+ opt-in
  `save_record`/`update_media`/`bulk_tag`) — RLS is the only scope, same as a dashboard user.
